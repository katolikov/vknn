How VKNN works

VKNN turns an ONNX neural network into a compact plan file on your workstation, then executes that plan on a phone's GPU through Vulkan compute — with the CPU kept out of the hot path. This page is an interactive tour of that journey. Click any block in a diagram (or use Tab + Enter) for a plain-English explanation of what it does and why it exists; the architecture reference has the full detail.

The big picture

There are two halves. Compile once: vknn_compile reads the ONNX model, optimizes the graph, and writes a .vxm plan. Run many times: on the phone, the engine memory-maps that plan, builds GPU pipelines for it, and replays pre-recorded command buffers for every inference.

Inside a .vxm plan

A .vxm is a single flat file — no archive, no compression — laid out so the phone can memory-map it and start executing without unpacking anything. It stores what to compute (the optimized graphs) and the numbers to compute with (the weights). It deliberately stores no GPU-specific state: shaders live inside the engine binary and pipelines are built on the device, so one .vxm runs on any device the engine supports. Click a section:

What happens on run()

Loading already did the expensive work (pipelines, weight packing, autotune). A steady-state run() is deliberately boring — click through the steps:

  1. Bind inputs. You hand over plain fp32 arrays (or DMA-BUF file descriptors for zero-copy camera frames). Shapes are validated against the plan; token-index inputs are range-checked so a corrupt id can't read out of bounds.
  2. Pick the bucket. The session matches your bound input names + shapes against each compiled bucket and dispatches to the right one — that's how one VLM file serves image encode, prefill, and decode from the same run() call. A fixed-shape model skips the lookup.
  3. Move inputs to the GPU. Boundary inputs are packed into the GPU's native layout. On a whole-graph-GPU model, 8-bit image inputs upload raw and convert on the GPU; DMA-BUF inputs are already there (zero copies on a unified-memory phone).
  4. Replay the pre-recorded commands. No per-op decisions happen now: the engine submits the command buffers it recorded at load, one vkQueueSubmit + fence per chunk (chunks of ≤500 nodes keep the GPU watchdog happy on second-long workloads).
  5. Read back only what you need. Outputs unpack to plain fp32. An LLM can skip the download entirely: an on-GPU argmax turns the 150k-wide logits row into an 8-byte answer, and KV-cache tensors never leave the device — resident links copy them in place for the next token.

The rules the design keeps

Compile once, run anywhere

A .vxm carries nothing device-specific. Pipelines, layouts, and tuning are rebuilt per device — and cached, so only the first load pays.

The GPU is the engine

Every executable op has a Vulkan kernel. The CPU backend is the correctness oracle and a fallback that announces itself — never a silent slow path.

fp16 storage, fp32 math

Activations and weights live in fp16 to halve bandwidth; every kernel accumulates in fp32, and results are checked against an onnxruntime golden.

No hidden knobs

The engine reads no environment variables. Everything is a vknn::Config field or a setHint — see Config.
